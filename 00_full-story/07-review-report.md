# コードレビュー報告書 -- 05-implementation.ts

レビュー対象: メッセージCRUD API（Hono + Zod）
レビュアー: AI（Claude）
日付: 2026-03-29


## 総合評価

実用に耐えうるレベルの実装。Zodによるバリデーション、論理削除、編集時間制限など基本設計は妥当。ただし本番投入前に対応すべき項目がいくつかある。


## セキュリティ

### [高] SQLクエリの動的組み立て

search エンドポイントでクエリ文字列を条件分岐で連結している（97-117行付近）。D1のプリペアドステートメントを使っているため即座にSQLインジェクションにはならないが、文字列連結によるクエリ組み立ては保守性に難がある。クエリビルダーの導入を検討すべき。

修正案: drizzle-orm や kysely のようなクエリビルダーでWHERE句を組み立てる。


### [中] 認証情報の取得方法

getAuth関数が `c.get('auth')` でミドルウェアから注入された認証情報を取得している。型安全ではあるが、ミドルウェアが適用されていないルートでは undefined が返る。ルーターのグループ化で認証ミドルウェアの適用漏れを防ぐ構造にしたほうがいい。

修正案: `app.use('/channels/*', authMiddleware)` のようにパスパターンで一括適用する。


### [低] リアクション削除のチャンネルアクセス検証

リアクション削除エンドポイントで `verifyChannelAccess` が呼ばれていない。他のチャンネルのメッセージのリアクションを操作できる可能性がある。

修正案: リアクション追加と同様に `verifyChannelAccess` を追加する。


## パフォーマンス

### [中] メッセージ一覧のN+1リスク

現状はJOINで取得しているため問題ない。ただしリアクションやアタッチメントをレスポンスに含める場合、追加クエリが必要になる。将来的にN+1が発生しやすい構造になっている。

修正案: リアクション・アタッチメントはサブクエリかJSON集約で1クエリに収める。PostgreSQLの `json_agg` が使える。


### [低] 検索のCOUNTクエリ

全文検索で件数取得と本体取得を別クエリで実行している。件数が不要なケースではCOUNTクエリを省略するオプションがあるとよい。

修正案: `include_total=true` のようなクエリパラメータで制御する。


## 保守性

### [中] エラーメッセージのハードコード

エラーメッセージが各所に日本語で直書きされている。国際化対応やメッセージの一元管理を考えると、定数ファイルに切り出したほうがいい。

修正案: `const ERRORS = { UNAUTHORIZED: '認証が必要です', ... }` のような定数オブジェクトにまとめる。


### [低] マジックナンバー

編集可能時間の `5` が関数のデフォルト引数に埋め込まれている。設定値として外出しにすると変更時の影響範囲が明確になる。

修正案: `const EDIT_WINDOW_MINUTES = 5` を定数として定義する。


### [低] レスポンス型の不統一

一覧取得は `{ data, pagination }` 形式だが、単体取得はオブジェクトを直接返している。クライアント側の型定義が煩雑になる。

修正案: 単体取得も `{ data: message }` でラップする方針を検討する。


## 良い点

- Zodスキーマが OpenAPI 仕様と一致している（content の maxLength: 4000）
- 論理削除の採用で監査ログとの整合性が取れている
- 編集時間制限のロジックが明確で、テストしやすい構造になっている
- ゲストユーザーの権限制御がパブリックチャンネルに限定されている点は適切
- HTTPステータスコードの使い分けが正確（409 Conflict、410 Gone など）
