プロダクトマネージャーが書いた自然言語の仕様書を AI に渡すと、 OpenAPI 3.0 仕様 + TypeScript 型定義 + Zod バリデーションスキーマが生成される。 手作業で起きがちな REST 原則違反を 20 件すべて解消した状態で出力される。

Before / After を見る プロンプトを確認する
IN

入力

自然言語で書かれた機能仕様書（feature-spec.md）。 ユーザー権限、タスク管理、ラベル、コメントなど 130 行のプロダクト要件。

AI

処理

Claude Code がREST設計原則を適用。リソース指向URL、HTTPメソッドの使い分け、 エラー設計、ページネーション、型安全性を自動で組み込む。

OUT

出力

OpenAPI 3.0.3 仕様（1,100行超）と TypeScript 型定義 + Zod スキーマ（350行超）。 Swagger UI やコード生成ツールにそのまま投入できる。

主要な改善点

手作業 API から AI 生成 API への変化を 5 つに凝縮

動詞入り URL がリソース指向に

Before

POST /api/createProject
POST /api/deleteProject
GET /api/getProjects

After

POST /api/v1/projects
DELETE /api/v1/projects/{id}
GET /api/v1/projects

バラバラなレスポンスが統一エンベロープに

Before -- 4種類が混在

{ success: true }
{ ok: true }
{ result: "ok" }
{ deleted: true }

After -- 統一構造

{ data: T }
{ data: T[], meta: {...} }
204 No Content

エラー設計が RFC 7807 準拠に

Before -- 全エラーが 500

{ error: "なんかエラー" }

After -- 構造化エラー

{ type: "https://api.../problems/not-found",
  title: "リソースが見つかりません",
  status: 404,
  detail: "タスクID: 550e... は存在しません" }

生の string 型が Zod バリデーション付きに

Before -- 型なし

body: { email, password }

After -- ランタイム検証付き

z.object({
  email: z.string().email(),
  password: z.string().min(8).max(128),
})

全件返却がカーソルベースページネーションに

Before -- 全件返却

GET /api/tasks/getAll
※ 件数が多くても全部返す

After -- ページネーション

GET /api/v1/projects/{id}/tasks
    ?cursor=xxx&limit=20
meta: { nextCursor, hasMore, totalCount }

import { z } from "zod"

// === ブランド型: Zod でランタイム検証 ===
const uuidSchema = z.string().uuid()
const dateTimeSchema = z.string().datetime()
const dateSchema = z.string().date()
const hexColorSchema = z.string().regex(
  /^#[0-9a-fA-F]{6}$/,
  "HEXカラーコード形式で指定"
)

type UUID = z.infer<typeof uuidSchema>
type DateTimeString = z.infer<typeof dateTimeSchema>
type DateString = z.infer<typeof dateSchema>

// === ページネーション（ジェネリクス） ===
const paginationMetaSchema = z.object({
  nextCursor: z.string().nullable(),
  hasMore: z.boolean(),
  totalCount: z.number().int().min(0),
})

function paginatedResponseSchema<T extends z.ZodTypeAny>(
  itemSchema: T
) {
  return z.object({
    data: z.array(itemSchema),
    meta: paginationMetaSchema,
  })
}

function singleResponseSchema<T extends z.ZodTypeAny>(
  itemSchema: T
) {
  return z.object({ data: itemSchema })
}

// === RFC 7807 エラー ===
const problemDetailSchema = z.object({
  type: z.string().url(),
  title: z.string(),
  status: z.number().int().min(400).max(599),
  detail: z.string().optional(),
  instance: z.string().optional(),
})

const validationProblemDetailSchema = problemDetailSchema.extend({
  errors: z.array(z.object({
    field: z.string(),
    message: z.string(),
    code: z.string(),
  })),
})

const taskPrioritySchema = z.enum([
  "low", "medium", "high", "urgent"

const createTaskRequestSchema = z.object({
  title: z.string().min(1).max(200),
  description: z.string().max(5000).optional(),

// === ステータス遷移ルール ===
const ALLOWED_STATUS_TRANSITIONS: Readonly<
  Record<TaskStatus, readonly TaskStatus[]>
> = {
  todo: ["in_progress", "cancelled"],
  in_progress: ["in_review", "todo", "cancelled"],
  in_review: ["done", "in_progress"],
  done: ["in_progress"],
  cancelled: ["todo"],
} as const

function isValidStatusTransition(
  from: TaskStatus,
  to: TaskStatus
): boolean {
  return ALLOWED_STATUS_TRANSITIONS[from].includes(to)
}

REST 原則違反 -- 全 20 件

Before の API 設計で検出した問題点の一覧。AI 生成版ではすべて解消されている。

# カテゴリ 問題点
1レスポンス設計登録時にトークンを返さない
2認証設計トークンリフレッシュ機構がない
3認証設計独自ヘッダー（標準の Bearer を使っていない）
4URL設計パスに動詞が含まれている
5メソッド設計更新・削除にも POST を使用
6URL設計リソースIDの渡し方が不統一
7レスポンス設計エンベロープ形式がバラバラ
8ページネーション一覧系で全件返却
9URL設計親子リソースの階層が未表現
10URL設計パス命名規則の不統一
11バリデーションステータス遷移ルール無視
12レスポンス設計更新後のリソースが返らない
13フィルタリング検索・絞り込み機能がない

## REST 設計原則

URL設計:
- リソース指向（パスに動詞を含めない、名詞の複数形を使う）
- 親子関係はパスのネストで表現する（/projects/:projectId/tasks/:taskId）
- APIバージョニングはURLプレフィックス方式（/api/v1/...）
- リソースIDはパスパラメータで渡す（クエリパラメータではなく）

HTTPメソッド:
- GET: 取得（副作用なし）
- POST: 新規作成
- PATCH: 部分更新
- PUT: 全置換またはべき等な操作（担当者設定、ラベル付与など）
- DELETE: 削除

レスポンス設計:
- 統一エンベロープ -- 単一: { data: T }、一覧: { data: T[], meta: PaginationMeta }
- 作成: 201 + 作成されたリソースを返す
- 更新: 200 + 更新後のリソース全体を返す（クライアントが再取得せずに済む）
- 削除: 204 No Content（ボディなし）
- エラー: RFC 7807 Problem Details 準拠（type, title, status, detail, instance）
- ステータスコードを適切に使い分ける（200, 201, 204, 401, 403, 404, 409, 422, 429）

ページネーション:
- カーソルベース（cursor + limit パラメータ）
- デフォルト20件、最大100件
- meta に nextCursor, hasMore, totalCount を含める

認証:
- Bearer トークン方式（Authorization: Bearer <token>）
- accessToken + refreshToken のペア発行
- JWT を想定

フィルタリング・ソート:
- フィルタはクエリパラメータで表現
- ソートは sort（フィールド名） + order（asc/desc）

データ形式:
- JSON のフィールド名は camelCase で統一
- 日時は ISO 8601 / UTC
- ID は UUID v4

## openapi.yaml の要件

- 全エンドポイントに operationId を付与する
- 全エンドポイントのリクエストボディとレスポンスに example を記載する
- 共通エラーレスポンス（401, 403, 404, 409, 422, 429）を components/responses に定義
- 429 TooManyRequests に Retry-After / X-RateLimit-* ヘッダーを定義
- パラメータのバリデーション制約を漏れなく定義
- スキーマの required フィールドを正確に指定

## types.ts の要件

- 全型に Zod スキーマを定義（z.infer<typeof schema> で型を導出）
- UUID, DateTimeString, DateString は Zod カスタムバリデーション付き
- ページネーション/シングルレスポンスはジェネリクスで汎用化
- ユニオン型は z.enum で定義
- ステータス遷移ルールを定数 + 判定関数として実装
- HEXカラーコードは正規表現バリデーション
